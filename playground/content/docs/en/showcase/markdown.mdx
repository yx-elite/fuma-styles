## Typography

Plain text in all its forms. Most of a study note is paragraphs and headings, so these matter more than any component.

### Heading level 3

A level-3 heading splits a section into parts. It is also listed in *On this page*, indented under its parent.

#### Heading level 4

A level-4 heading is for small groups inside a part. It is not listed in *On this page* by default.

##### Heading level 5

Level 5 is rare in notes, but it should still look like a heading and not like bold text.

###### Heading level 6

Level 6 is the smallest heading. It often looks close to body text, so it needs a clear style of its own.

### Paragraphs

A single paragraph of a reasonable length. Body text should be comfortable to read for a long time: a line length of roughly 60 to 80 characters, enough space between lines, and a colour with good contrast that is not pure white on pure black.

A second paragraph follows straight after. The space between paragraphs should make the break clear without breaking the flow. Study notes often have several short paragraphs in a row, each covering one idea, so this spacing shows up everywhere.

A very long paragraph, to check how dense text reads when it runs on. Caches keep a copy of data closer to where it is used, so later reads are faster and cheaper. The trade-off is freshness: a cached copy can become stale when the original changes, and every caching design has to decide how stale is acceptable. Some systems expire entries after a fixed time, some remove entries when the original changes, and some do both. Choosing well depends on how often the data changes, how expensive a miss is, and how much harm an old value can do. A product price that is a minute old is usually fine; a bank balance that is a minute old may not be.

Short line.

### Emphasis

Text can be **bold** for key terms, *italic* for gentle emphasis or titles, and ***bold italic*** when both apply. ~~Strikethrough~~ marks something removed or outdated. Bold can also sit inside a sentence: the **origin** is where the original data lives.

Mixed in one paragraph: a **cache hit** is fast, a *cache miss* is slow, and an ~~eviction~~ *expiry* removes old entries. Some notes use <mark>highlighted text</mark> for the one thing to remember.

### Inline code

Inline code marks names, values and commands: set `Cache-Control` to `max-age=3600`, or run `dig example.com` to look up a domain. Long inline code should wrap or scroll sensibly: `arn:aws:s3:::example-bucket-with-a-very-long-name/path/to/an/object.json`.

Inline code inside bold and links: **`TTL` means time to live**, and see [the `create` command](/docs/installation).

### Keyboard keys and small text

Press <kbd>Cmd</kbd> + <kbd>K</kbd> to search, or <kbd>Ctrl</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> in an editor.

Chemical and maths notation uses subscript and superscript: H<sub>2</sub>O, 2<sup>10</sup> = 1,024, and 10<sup>-3</sup> seconds.

<abbr title="Time to live">TTL</abbr> is an abbreviation with a hover title.

<small>Small print for a side remark or a source note.</small>

### Line breaks

A line can end with a hard break  
so the next line starts below it without a new paragraph.  
Useful for addresses or short stacked facts.

### Horizontal rule

Text above the rule.

---

Text below the rule. A rule separates parts of a page that have no heading between them.

### Term and meaning lists

The format used across the notes: a term in code, then what it means.

- `TTL`: how long a cached answer stays valid.
- `hit`: the answer was found in the cache.
- `miss`: the answer had to come from the origin.
- `eviction`: an entry was removed to make space.

The same with bold terms:

- **Write-through:** every write goes to the cache and the origin at once.
- **Write-back:** writes go to the cache first and reach the origin later.
- **Cache-aside:** the application reads the cache and fills it on a miss.

### Long items

- A long list item that wraps over several lines. It checks the indent of the second line: the wrapped text should line up with the first word, not with the bullet, so a long item still reads as one block.
- A list item with two paragraphs.

  The second paragraph belongs to the same item. It needs the same indent and a little space above it.

- A list item with a code block inside:

  ```bash
  dig +short example.com
  ```

- A list item with a quote inside:

  > Quoted text inside a list item.

### Task list

- [x] Read the chapter
- [x] Write the notes
- [ ] Draw the diagram
- [ ] Do the practice questions
  - [x] Set 1
  - [ ] Set 2

### Exam scenarios

The pattern used at the end of each note:

- **Users worldwide, one Region, slow pages** → cache content at the edge, because it moves copies closer to users.
- **Data must survive a data centre failure** → spread across at least two zones, because one zone can fail on its own.
- **Old prices shown after an update** → shorten the TTL or clear the cache on change, because the cached copy is stale.

## Tables

Tables compare several things on several points. They must stay readable on a phone, which usually means scrolling sideways inside the table, not the page.

### Simple table

| Term | Meaning |
| --- | --- |
| Hit | Found in the cache |
| Miss | Fetched from the origin |
| Eviction | Removed to make space |

### Column alignment

| Left | Centre | Right |
| :--- | :---: | ---: |
| Region | 3 zones | 0.023 |
| Zone | 1+ data centres | 0.0125 |
| Edge location | Many cities | 0.0004 |

### Comparison table

| Storage type | Attached to | Shared | Typical use | Speed |
| --- | --- | --- | --- | --- |
| Block | One machine | No | Databases, boot disks | Fastest |
| File | Many machines | Yes | Shared folders | Fast |
| Object | Nothing (HTTP) | Yes | Backups, media, static sites | Good |

### Rich content in cells

| Setting | Example | Notes |
| --- | --- | --- |
| `Cache-Control` | `max-age=3600` | Seconds a copy stays fresh. See [Configuration](/docs/configuration). |
| `ETag` | `"33a64df5"` | A version tag; **changes** when the content changes. |
| `Vary` | `Accept-Encoding` | Keeps a separate copy per value. ~~Rarely~~ often needed. |

### Wide table

| Name | Type | Default | Region scope | Billing | Free tier | Encryption | Backups | Notes |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Example A | Block | 8 GiB | Zone | Per GiB-month | 30 GiB | Optional | Snapshots | Attached to one instance at a time |
| Example B | File | Elastic | Region | Per GiB used | 5 GiB | On by default | Automatic | Mounted by many instances at once |
| Example C | Object | Unlimited | Region | Per GiB + requests | 5 GiB | On by default | Versioning | Accessed over HTTPS, not mounted |

### Long text in cells

| Strategy | How it works | When to use it |
| --- | --- | --- |
| Cache-aside | The application checks the cache first. On a miss it reads the origin, then writes the result into the cache for next time. | Read-heavy data that can be a little stale, where only requested items should take up cache space. |
| Write-through | Every write goes to the cache and the origin together, so the cache is always current. | Data that is read soon after it is written and must not be stale. |

## Quotes and callouts

Callouts hold the few lines a reader must not miss. Each type needs its own colour and icon, readable in both modes.

### Blockquote

> A blockquote for a quoted definition or a source.

> A longer blockquote over several lines. It should be set apart from body text by an indent or a bar, without looking like a warning.
>
> It can have a second paragraph.

### Nested blockquote

> Outer quote.
>
> > Inner quote.

### Blockquote with a list

> Things to check before deploying:
>
> - The build passes
> - The cache is cleared
> - The DNS record points to the right place

### Callout types

<Callout type="warn" title="Warning">The `warn` type: something that can cost money or cause trouble.</Callout>

<Callout type="warn">A warning with no title, only a body.</Callout>

### Callout with rich content

<Callout type="info" title="Cache headers">

  - `max-age`: how long a copy stays fresh
  - `no-store`: never keep a copy

### GitHub alert syntax

The syntax used in the old GitHub handbook. Whether these render as callouts or plain quotes shows if the syntax is supported yet.

> [!NOTE]
> Surprising but harmless.

> [!TIP]
> A better or cheaper way.

> [!IMPORTANT]
> Outdated or easily confused.

> [!WARNING]
> Can lose data or cost money.

> [!CAUTION]
> Destructive and hard to undo.
