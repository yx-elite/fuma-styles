title: Caching basics
description: What a cache is, how hits and misses work, how long copies stay fresh, and the common strategies for keeping a cache in step with the original.
---

A cache keeps a copy of data close to where it is used, so repeated reads are faster and cheaper than going back to the original every time. Almost every fast system has one somewhere: in the browser, at the network edge, in front of a database, or inside the application itself.

## Key ideas

The building blocks first, then how long copies live, then the strategies.

![A client asks a cache, which asks the origin on a miss](/sample-diagram.svg)

### Hits and misses

Every read either finds the data in the cache or does not.

- `hit`: the data was in the cache and came back straight away.
- `miss`: the data was not there, so it came from the origin and was usually stored for next time.
- `hit ratio`: hits divided by all reads. A higher ratio means the cache is doing more of the work.

A cold cache, for example right after a restart, starts with a hit ratio of zero. It warms up as requests fill it.

### Freshness and TTL

A cached copy is only useful while it still matches the original closely enough.

- `TTL`: time to live, how long a copy counts as fresh, in seconds.
- `stale`: a copy whose original has changed, or whose TTL has run out.
- `invalidation`: removing or replacing a copy on purpose, before its TTL ends.

<Callout type="warn">
  A long TTL makes the cache faster but keeps stale data around longer. Pick it from how often the data changes and how much harm an old value does.
</Callout>

A product description can safely be cached for hours. A stock level probably for seconds. An account balance usually not at all.

### Eviction

A cache has limited space, so something has to go when it is full.

| Policy | Removes | Good for |
| --- | --- | --- |
| LRU | The entry used least recently | Most general workloads |
| LFU | The entry used least often | Data with stable favourites |
| FIFO | The oldest entry | Simple, predictable caches |
| TTL only | Entries whose time is up | Data with a natural expiry |

### Strategies

How the application, the cache and the origin work together.

- **Cache-aside:** the application reads the cache, and on a miss reads the origin and fills the cache itself. Only requested data is cached.
- **Read-through:** the cache sits in front of the origin and fetches misses on its own. The application only talks to the cache.
- **Write-through:** every write goes to the cache and the origin together. The cache is never stale, but writes are slower.
- **Write-back:** writes go to the cache first and reach the origin later. Fast, but data can be lost if the cache fails first.

### Where caches live

1. **Browser:** keeps files the user has already downloaded.
2. **Edge (CDN):** keeps copies in many cities, close to users.
3. **Application:** keeps results in memory, inside the running program.
4. **Database cache:** an in-memory store in front of a database.

Each layer has its own TTL, so a change at the origin can take a while to show up everywhere.

### Exam scenarios

- **Users worldwide, slow page loads** → cache static content at the edge, because copies sit closer to users.
- **Database overloaded by repeated reads** → put an in-memory cache in front of it, because most reads become hits.
- **Old content still shown after an update** → invalidate the cached copies or version the file names, because the TTL has not run out yet.
- **Writes must never be lost** → avoid write-back, because unsaved writes live only in the cache.
